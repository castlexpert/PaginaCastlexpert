Antes de cotizar

2. Análisis previo — lo que se define antes de cotizar

Estas decisiones se toman una sola vez, pero se heredan a lo largo de toda la migración.

01

Inventario de módulos y submódulos

Mapeo completo del sistema: qué formas pertenecen a qué dominio de negocio (facturación, inventario, RRHH, etc.) y sus relaciones entre sí.

02

Priorización de migración

Orden de migración según criticidad para el negocio, dependencias técnicas entre módulos, y valor rápido para el cliente.

03

Modelo de seguridad a heredar

Definición temprana de cómo se replica el control de acceso — decisión que impacta la arquitectura completa.

Seguridad basada en menús de Forms
  • El acceso se controla mediante roles asociados a opciones de menú dentro de Forms.
  • Migra hacia un sistema de rutas protegidas + roles en React (route guards) y middleware de autorización en Node.
  • Requiere mapear cada opción de menú Forms a una ruta/permiso equivalente en la nueva plataforma.
Seguridad por sistema a medida
  • El control de acceso vive en tablas propias del negocio (perfiles, permisos por pantalla/acción, etc.).
  • Se preserva el modelo tal cual — se traduce la tabla de permisos existente a un servicio de autorización en Node (RBAC/ABAC según el caso).
  • Menor riesgo de pérdida de reglas de negocio, porque la fuente de verdad ya está en base de datos.
Por qué se define primero: el modelo de seguridad no es una pantalla más — es una regla de negocio transversal. Cambiar de enfoque a mitad de la migración implica retrabajo en todos los módulos ya migrados.

Diseño de pantallas

3. Dos rutas para capturar el diseño de pantalla

Ambas parten de la misma lógica de negocio migrada; lo que cambia es cómo se define la distribución visual de campos.

XML del Forms (Forms2XML)
↓
Ruta A

Migración libre desde XML

El agente interpreta directamente la estructura del XML (bloques, orden de items, agrupaciones) y propone la distribución de campos.

  • Más rápida — no requiere insumos adicionales del cliente.
  • El resultado sigue la lógica interna de Forms, no necesariamente el “look” visual percibido por el usuario final.
Ideal para: pantallas CRUD estándar, formularios internos, módulos donde el diseño exacto no es crítico.
Ruta B

Migración guiada por captura de pantalla

El cliente entrega un print screen del formulario en ejecución; el agente combina XML + imagen para replicar la distribución visual real de los campos.

  • Mayor fidelidad visual al formulario que el usuario final ya conoce.
  • Reduce curva de adaptación del usuario final al nuevo sistema.
Ideal para: pantallas de alto uso diario, formularios con layout no estándar, módulos sensibles a la experiencia de usuario.
Ambas rutas convergen en: componente React + endpoints Node.js

Validación

4. Ciclo de pruebas compartido

Una vez migrado el lote, se habilita un espacio de validación conjunta antes de cerrar el módulo.

Repositorio compartido
→
Cliente prueba pantallas
→
CastleXpert revisa hallazgos
→
Ajustes puntuales
→
Nueva versión en repositorio

Este ciclo se repite tantas veces como sea necesario dentro del tiempo prudencial acordado por módulo, antes de pasar a producción.
